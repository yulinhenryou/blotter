# M1 plan — CFR on Kuhn and Leduc (Rust)

Status: **accepted (2026-11-04)**; D1–D3 decided as recommended (§0.1). Acceptance criteria:
`ROADMAP.md` → M1. Progress: Tasks 1–4 merged; Task 5 in review.

M1 builds the readable, tabular half of ADR-0015: a generic extensive-form game, two small poker
games, regret matching, CFR / CFR+ / DCFR, and an exact best response. Everything is checked
against results that do not come from this code: the hand-derived Kuhn equilibrium, hand-computed
best responses, and the published Leduc rules. The vector-form solver for hold'em subgames is M2.

The order is deliberate: **best response before CFR.** Exploitability is the measuring stick for
every CFR variant, so it is built and verified first, against the closed-form Kuhn equilibrium.

`crates/cards` is not used in M1 (Kuhn and Leduc have their own tiny decks). `bindings` is not

### 1.2 Game representation

A game is described once through a trait, then **flattened into an arena** that every algorithm
reads:

```rust
pub enum NodeKind<S> {
    Terminal { payoff_p1_chips: i64 },          // zero-sum: P2 gets the negative
    Chance { outcomes: Vec<(u32, S)> },         // integer weights; probability = weight / sum
    Decision { player: Player, infoset_key: String, actions: Vec<(Action, S)> },
}

pub trait Game {
    type State;
    fn root(&self) -> Self::State;
    fn node(&self, state: &Self::State) -> NodeKind<Self::State>;
}
```

`GameTree::build(&game)` walks the game once and stores nodes in a `Vec<Node>` where children are
referred to by **index** (`usize`), not by reference. Information-set keys are interned into dense
indices `0..n`, so regrets and strategies are plain `Vec<f64>` rows addressed by index.

Why an arena: Kuhn and Leduc trees are small, every CFR iteration walks the whole tree, and
indices sidestep the ownership problems of a tree of references (`Rc<RefCell<…>>`). The tree is
built once and then only borrowed immutably (`&GameTree`), while the solver state (regrets,
strategy sums) is borrowed mutably — two separate values, so the borrow checker is satisfied
without interior mutability.

Payoffs are integer chips and chance probabilities are integer weights, so the exact best response
(D1) can read them without rounding. Nodes are stored in post-order (every child has a smaller
index than its parent), so iterating indices upwards is a bottom-up pass.

### 1.3 CFR variants

One driver, parameterized by a variant (an `enum` with data):

| Variant | Regret update | Strategy average weight on iteration t | Updates |
|---|---|---|---|
| CFR | cumulative regret | 1 | simultaneous |
| CFR+ | regret matching+ (clip at 0 after each update) | t | alternating |
| DCFR(α, β, γ) | after adding r^t: positive regrets × t^α/(t^α+1), negative × t^β/(t^β+1) | t^γ (equivalent to the paper's (t/(t+1))^γ discount) | alternating, as in the paper's experiments |

The exact update order and averaging details of CFR+ and DCFR were taken from the papers in Task 5
(Tammelin 2014; Tammelin et al. 2015; Burch, Moravčík & Schmid 2019; Brown & Sandholm 2019) and
are written in `MATH.md` §2.3–2.4, including the single update rule all three variants share.

### 1.4 Best response

Exact best response by backward induction over **information sets**, not over tree nodes: the
best-responding player cannot distinguish histories inside one information set, so the choice at
an information set maximizes the sum of counterfactual values over all its histories (weighted by
the opponent's and chance's reach). With perfect recall this can be done by processing the
player's information sets from the deepest to the shallowest. Derivation: `MATH.md` §2.7
(Task 3).

Units: Kuhn and Leduc values and exploitability are in **chips** (ante = 1). Exploitability uses
the convention of `MATH.md` §1.1, $e = (b_1 + b_2)/2$.

## 2. Tasks

Each task is one PR (D3). "Math" is derived in the session before the code; "Rust" is
what the code teaches.

### Task 1 — Kuhn equilibrium by hand (docs only)

- `MATH.md` §1.2: dominance reductions; the indifference conditions; the one-parameter family
  (P1 bets J with α ∈ [0, 1/3], bets K with 3α, never bets Q, calls with Q with α + 1/3; P2 calls
  a bet with Q with 1/3, bluffs J after a check with 1/3); the value −1/18 and why it does not
  depend on α; why Q betting is strictly worse than checking.
- Verified by: Henry reviews the derivation. (Task 3 then checks it mechanically.)

### Task 2 — Game trait, arena tree, Kuhn

- Files: `game.rs`, `tree.rs`, `games/kuhn.rs`, tests.
- Tests (all counts derived by hand in the PR): Kuhn has 6 deals, 5 betting sequences per deal,
  hence 30 terminal histories; 12 information sets (each player: 3 cards × 2 decision points);
  terminal utilities are zero-sum; chance probabilities sum to 1.
- Rust: `enum` with data and exhaustive `match`; traits with an associated type (`type State`);
  `Vec` ownership and moving values into it; indices instead of references; `HashMap` for
  interning keys; `&self` vs `&mut self`; `#[derive(Clone, Copy, Debug, PartialEq, Eq)]` and why
  `Copy` is fine for `Player` but not for `String`.

### Task 3 — Exact best response and exploitability

- Math: `MATH.md` §2.7 — best response over information sets; game value; exploitability.
- Files: `value.rs`, `strategy.rs`, `best_response.rs`, tests.
- Tests:
  - AC3: best-response values of each player against the uniform random strategy in Kuhn,
    computed by hand (in the PR, as fractions) and matched exactly.
  - The closed-form equilibrium from Task 1 (for example α = 0 and α = 1/6, both rational) has
    exploitability exactly 0 and value exactly −1/18. This is the independent anchor every CFR
    variant is later measured against.
  - A deliberately perturbed equilibrium has exploitability > 0.
- Rust: generics with trait bounds (`fn best_response<V: Value>(…)`, D1); slices
  (`&[f64]`) for strategy rows; iterators (`zip`, `map`, `sum`); typed errors with `Result` for
  strategies whose rows do not match the tree.

### Task 4 — Regret matching and vanilla CFR

- Math: `MATH.md` §2.1 (regret matching and its no-regret bound) and §2.2 (counterfactual value,
  regret decomposition, average strategy → ε-equilibrium).
- Files: `regret.rs`, `cfr.rs`, tests.
- Tests:
  - AC1: value of the average strategy within tolerance of −1/18 (tolerance **[set after first
    measurement]**); exploitability decreases (checked at a few iteration counts, not
    monotonically per iteration — CFR's exploitability is not guaranteed to fall every
    iteration).
  - AC2, from Task 1: P(bet | Q) ≈ 0; |P(bet | K) − 3·P(bet | J)| small (a difference, not a
    ratio, because CFR may converge to α ≈ 0); P(call | Q, check–bet) ≈ P(bet | J) + 1/3;
    P2's calls with Q and bluffs with J ≈ 1/3.
  - AC5 (proptest): every current and average strategy row sums to 1 within 1e-12 and is
    non-negative; regrets are finite.
- Rust: why the tree and the solver state are separate values (`Cfr<'t>` borrows the tree, owns
  its tables; disjoint field borrows); `f64` and its edge cases (division by zero → uniform
  strategy); `proptest` strategies.
- As implemented: the passes are loops over the post-order arena (as in Task 3), not recursion.
  Besides AC1/AC2/AC5, property tests check the bounds of `MATH.md` §2.2 on games with Kuhn's
  tree and random payoffs. The tolerances and the measured run are in `MATH.md` §2.2.

### Task 5 — CFR+ and DCFR

- Math: `MATH.md` §2.3–2.4 from the papers: regret matching+, alternating updates, weighted
  averaging, DCFR's discounts; which parameter settings correspond to which variant.
- Tests: Kuhn AC1/AC2 for each variant; AC5 extended — CFR+ cumulative regrets are never
  negative (proptest).
- Rust: `enum` variants with data (`Dcfr { alpha, beta, gamma }`); `impl` blocks and methods;
  avoiding duplicated code with a small trait or a `match` in one place.
- As implemented: one `match` (`Variant::schedule`) yields the factors for positive and negative
  regrets and the averaging weight of iteration t; one pass function serves simultaneous and
  alternating updates. The papers' proof of CFR+ needed the repair by Burch et al. (2019) for
  alternating updates; `MATH.md` §2.3 derives the bound for all variants, which the property
  test checks (with random DCFR parameters). Exact fixtures from an independent rational
  implementation pin the update order. DCFR rejects α < 0 (see `MATH.md` §2.3, Lemma 4).

### Task 6 — Leduc and the convergence curve

- Math: `MATH.md` §1.3 — the exact rule variant (Southey et al. 2005: two suits of J, Q, K;
  ante 1; bet size 2 in round one and 4 in round two; at most one bet and one raise per round;
  pair with the board wins, otherwise the higher card), checked against the paper; the number of
  information sets derived by hand and asserted in a test.
- Files: `games/leduc.rs`, `examples/leduc_convergence.rs`, the plotting script (D2),
  `docs/results/m1-leduc-convergence.{csv,svg}` plus a short `docs/results/README.md` entry with
  the exact command, commit hash and machine.
- Tests: AC4 — exploitability at a larger iteration count is lower than at a smaller one, for each
  variant (counts chosen so the test runs in seconds; see risks).
- Rust: `examples/` vs `src/bin/`; writing CSV with `std::io::Write` and `BufWriter`; `?` for
  I/O errors in `main() -> Result<(), Box<dyn Error>>`.

### Task 7 — Benchmarks and closing M1

- `benches/cfr.rs`: criterion benches for one CFR iteration on Kuhn and on Leduc, per variant.
- Run locally in release mode; record results with the machine description, toolchain and commit
  in `docs/results/README.md`. Baseline only — no targets, no comparisons with other solvers.
- Close M1: acceptance evidence table in this file (§4), `ROADMAP.md` and `CLAUDE.md` status.

## 4. Risks and open questions

| Risk | Mitigation |
|---|---|
| Leduc tests too slow in CI's debug build | Keep iteration counts small in `cargo test`; long runs live in the example (release mode). If needed, `[profile.test] opt-level = 1`, decided from a measurement |
| CFR converges to a different α each run (Kuhn has a family of equilibria) | Tests check the structure of the family, not a single α (Task 4) |
| Our Leduc variant differs from the published one, so published numbers are not comparable | Rules checked line by line against Southey et al. (2005) in Task 6; information-set count derived and tested |
| Paper details recalled wrongly (update order, averaging) | Taken from the papers during the derivation; disagreements with this plan are fixed in the plan, not in the code silently |
| Best response over tree nodes instead of information sets (a classic bug that overstates exploitability) | Task 3's exact tests against hand-computed values catch it |
